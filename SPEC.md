# Radar 2.0 — Фаза 1 (нулевая стоимость, ~1 день) Specification

## Overview

Два независимых, детерминированных улучшения без единого дополнительного LLM-вызова: Proof-of-Traction фильтр через OpenSSF Scorecard (с fallback), замена самописных GitHub HTTP-вызовов на `ghapi`.

Целевая архитектура зафиксирована в `Radar_2.0_Архитектура_и_Roadmap_v4.md` — этот SPEC описывает только детали реализации Фазы 1, полученные интервью через `spec`. Ничего из архитектуры v4 здесь не пересматривается.

**Изменение объёма (2026-08-01):** третий пункт (`less-tokens`) исключён из Фазы 1 и отложен в Фазу 2 — см. "Отложено в Фазу 2" ниже. Причина: README/RepoMap-контент, который `less-tokens` должен был сжимать, в кодовой базе не существует — ни `analyze.py`, ни `patterns.py` не загружают README или RepoMap репозитория. Это отдельный, ещё не реализованный пайплайн Фазы 2 (README-fetch + llm-tldr, по Roadmap v4), а не самостоятельная оптимизация существующего контекста.

## Goals

- [ ] Отсекать спам-фермы/незрелые репозитории ДО первого LLM-вызова через OpenSSF Scorecard, с graceful fallback на пороговый фильтр
- [ ] Заменить сырые `requests`-вызовы к `api.github.com` на `ghapi`

## Tech Stack

- Python 3 (без изменений)
- Новая зависимость: `ghapi` (fast.ai) — добавить в требования проекта
- OpenSSF Scorecard REST API (`api.securityscorecards.dev`) — публичный, без ключа

## Detailed Requirements

### 1. Proof-of-Traction фильтр (Scorecard + fallback)

**Уточнение по факту реализации (найдено в ходе Milestone 1, 2026-08-01):** пороговый fallback-фильтр (forks/stars, watchers/stars, bot-паттерны), описанный ниже как "без изменений от v4", в кодовой базе не существовал — `filter.py` содержал только keyword/topic-фильтр (`is_relevant()`), без данных о forks/watchers/коммитах в принципе. Работа над пунктом 1 разделена на два явных подпункта:

- **1A** — `scorecard.py` + интеграция в `filter.py`, ghapi-миграция (пункт 2). Реализуется как описано ниже, без изменений.
- **1B** — реализация недостающего порогового fallback-фильтра: добавить получение `forks_count`, `watchers_count` и данных о последних N коммитах в `radar_step0.py` (рядом с существующим сбором title/description/url/score/source/topics); написать `passes_traction_filter()`, реализующую условие из раздела "Пороговый fallback-фильтр" ниже. Дополняет `scorecard.py`, не заменяет его — вызывается в ветках `NO_DATA`/`UNAVAILABLE`.

**Временное состояние (честно задокументировано, не скрытая дыра):** до завершения 1B ветки `NO_DATA`/`UNAVAILABLE` в `check_scorecard()`/`filter.py` используют существующий `is_relevant()` (только keyword/topic) как временный fallback. После завершения 1B — заменяется на `passes_traction_filter()`.

Порядок реализации в рамках этой сессии: 1A → 1B, оба входят в Фазу 1 (не откладываются).

**Модуль:** новый файл `scorecard.py` в корне репозитория. `filter.py` импортирует и вызывает его — вся логика запроса/классификации/fallback изолирована в `scorecard.py`, `filter.py` не знает деталей HTTP.

**Функция:** `check_scorecard(owner, repo) -> ScorecardResult`

Возвращает один из трёх исходов:
| Исход | Условие | Поведение в Фазе 1 |
|---|---|---|
| `OK(score)` | Scorecard ответил 200, есть числовой `score` | Если `score < 4` → отсев (не проходит фильтр). Если `score >= 4` → проходит |
| `NO_DATA` | Scorecard ответил, но по репозиторию нет данных (404 / `score is None`) | Откат на пороговый фильтр |
| `UNAVAILABLE` | Timeout или HTTP-ошибка сети (5xx, connection error) | Откат на пороговый фильтр |

**Порог отсева:** `score < 4` (не 4-5 — конкретное число, константа `SCORECARD_MIN_SCORE = 4` в `scorecard.py`).

**Разделение причин, объединение последствий:** `NO_DATA` и `UNAVAILABLE` — два разных случая на уровне возвращаемого значения функции, с отдельными счётчиками (`metrics["score_missing"]`, `metrics["score_timeout"]`), которые пишутся в stdout в конце прогона `filter.py`/`radar_step0.py` (без персистентного хранилища метрик в Фазе 1 — просто print). Дальше по пайплайну оба случая ведут к одному и тому же: fallback на пороговый фильтр. `filter.py` не содержит отдельной ветки логики на `NO_DATA` vs `UNAVAILABLE` — только на "есть валидный score" vs "нет".

**Пороговый fallback-фильтр** (без изменений от v4): `forks/stars >= 0.03 AND watchers/stars >= 0.01 AND` отсутствие bot-паттернов в последних коммитах (regex).

**Кэш:** не нужен. Каждый репозиторий проходит через `filter.py` практически один раз при первом обнаружении — повторный вызов Scorecard не проблема, кэш добавил бы сложность без наблюдаемой пользы.

### 2. ghapi — замена сырых GitHub-вызовов

**Уточнение scope (по факту, не по первоначальному предположению):** реальные вызовы к `api.github.com` есть только в `radar_step0.py`, в двух функциях — `fetch_github()` и `fetch_awesome_lists()` (обе используют `requests.get(..., timeout=10)`). Остальные файлы (`analyze.py`, `update_assessments.py`, `check_model_updates.py`, `fetch_analysts.py`) вызывают Anthropic API, Telegram Bot API, Buttondown или страницу документации Claude — не GitHub API, и не входят в scope этой миграции.

**Функции, подлежащие миграции:**
- `fetch_github()` — поиск репозиториев (`GET /search/repositories`) → `ghapi` эквивалент поиска
- `fetch_awesome_lists()` — получение метаданных репозитория (`GET /repos/{owner}/{repo}`) → `ghapi` `repos.get`

**Timeout:** сохранить текущее значение `10` секунд как есть — не менять заодно с миграцией клиента, это отдельное решение вне scope Фазы 1.

**Retry:** не добавлять. `ghapi` — замена клиента 1:1, поведение при сетевых ошибках не меняется (один вызов = один результат, как сейчас).

**`fetch_hacker_news()` и `fetch_reddit()`** в том же файле не трогать — они не вызывают GitHub API.

**Telegram-вызовы** (`analyze.py`, `update_assessments.py`, `check_model_updates.py`) остаются на `requests` — осознанно, вне scope Фазы 1 (это отдельное, не связанное с ghapi решение).

## Отложено в Фазу 2

### less-tokens — сжатие промптов (было пунктом 3 Фазы 1, исключено 2026-08-01)

**Причина исключения:** пайплайн, который должен был поставлять README/RepoMap-контент в промпт, в кодовой базе отсутствует (README-fetch + RepoMap не реализованы ни в `analyze.py`, ни в `patterns.py`, ни где-либо ещё). `less-tokens` — оптимизация уже существующего контекста, а не самостоятельная функция; сжимать без источника нечего. По Roadmap v4 README-fetch + llm-tldr — пункт Фазы 2. `less-tokens` реализуется вместе с ним как единый пункт Фазы 2, не разрывается на два отдельных решения.

Формулировка ниже сохранена как есть (не переписана) — на момент реализации Фазы 2 её нужно будет заново сверить с фактическим состоянием кода на тот момент.

**Scope сжатия:** только README/RepoMap-контент репозитория, перед вставкой в шаблон промпта. Системная инструкция, служебные поля и структура промпта (в `analyze.py`/`patterns.py`) не сжимаются и не трогаются.

**Валидация перед продакшном:** прогнать 5-10 тестовых репозиториев до/после сжатия, подобранных осознанно (не первые попавшиеся):
- как минимум один репозиторий с очень коротким README
- как минимум один с очень длинным README
- как минимум один с нестандартным markdown (таблицы, code-блоки)

Сравнить: остаётся ли structured output от Haiku/Sonnet валидным (парсится в ожидаемые поля) до и после сжатия. Только после успешного прохождения этой проверки — включать `less-tokens` в продакшн-путь `analyze.py`/`patterns.py`.

## Non-Functional Requirements

1. Ни один из пунктов Фазы 1 не добавляет LLM-вызовов — весь код детерминированный (HTTP + regex/AST)
2. `scorecard.py` — новый файл, не модифицирует существующую сигнатуру `is_relevant()` в `filter.py`, вызывается отдельно
3. `python3 -m py_compile <файл>.py` после каждого изменённого файла, до commit (Правило CONSTITUTION)

## Security Considerations

- Scorecard API — публичный, без ключа, не передаёт секреты
- `ghapi`-миграция не меняет auth-модель (те же публичные unauthenticated GitHub-запросы, что и сейчас в `radar_step0.py`)

## Test Plan

- `py_compile` на каждый изменённый файл
- Ручной прогон `scorecard.py` на нескольких известных репозиториях (один заведомо живой с высоким score, один заведомо новый/маленький) — проверить, что `OK`/`NO_DATA`/`UNAVAILABLE` классифицируются верно
- Ручной прогон `radar_step0.py` после ghapi-миграции — сравнить результат до/после на одном и том же запросе (тот же набор репозиториев, те же поля)
