# CI-инвариант frontmatter — Specification (ред. 2)

## Overview

Единый источник статуса оценки (`status` во frontmatter `01_Assessments/*.md`, Фаза 2, коммит `098aecf`) закреплён в CONSTITUTION как правило («запись только через `write_verdict_entry()`»), но не enforced механически — 03.08.2026 production cron (старым кодом, ещё не знавшим о миграции) создал 2 файла без frontmatter в обход правила. Владелец выбрал **Вариант A**: backfill остаётся разовой миграцией, инвариант гарантируется на входе.

Первая редакция этого SPEC (интервью `/spec`, 2026-08-04) спроектировала единый механизм — job `lint_vault`, триггерящийся на `push` в ветку `vault`, детектирующий любой путь попадания невалидного файла. Реализация (коммит `5209556`): `check_frontmatter.py`, inline-гейт в `radar` job, `lint_vault` job с `rules: $CI_COMMIT_BRANCH == "vault" && $CI_PIPELINE_SOURCE == "push"`, фикс `backfill_frontmatter.py`.

**Находка при попытке выполнить Milestone 6 (реальный CI-прогон, приёмочный тест первой редакции)**: push в `vault`, выполняемый изнутри уже работающего CI job'а (`git push origin vault` через `GITLAB_PUSH_TOKEN` в конце `radar`/`publish`/`patterns`/`analysts`/`check_models`), **не создаёт отдельный pipeline** в текущей конфигурации этого GitLab-проекта. Подтверждено тремя независимыми фактами:
1. Публичный `GET /projects/.../pipelines?ref=vault` возвращает пустой список за всю историю проекта (сотни прогонов).
2. `radar` job завершается `success` многократно подряд, `git push origin vault` вызван голым (не в `if`/`||`) — упал бы job целиком, если бы push реально возвращал ошибку.
3. Владелец визуально подтвердил отсутствие pipeline с `ref=vault` в GitLab UI.

Значит `rules: $CI_COMMIT_BRANCH == "vault" && $CI_PIPELINE_SOURCE == "push"` у `lint_vault` — условие, которое **никогда не выполняется** в этой конфигурации. Это архитектурная ошибка первой редакции SPEC.md (предположила несуществующий триггер), не проблема тестового процесса — сам код `check_frontmatter.py`/`lint_vault`/`backfill_frontmatter.py` написан корректно относительно того, что от него ожидалось.

**Решение (эта редакция)**: разделить единый механизм на два, под два разных риска, вместо одного универсального job'а (Graceful Degradation, CONSTITUTION #6 — отказ/обход одного слоя не оставляет систему без защиты полностью):
- **Goal 2** (файл невалиден из-за одного из известных CI-путей записи в vault) — превентивный full-scan гейт в конце каждого job'а, пушащего в vault.
- **Goal 3** (файл невалиден из-за ручного push мимо CI, например `backfill_frontmatter.py`, запущенный локально) — детективный `lint_vault`, больше не на мёртвом push-триггере, а на `schedule`/`web`.

## Goals

- [x] Единственный переиспользуемый модуль валидации frontmatter (`check_frontmatter.py`) — реализовано, без изменений в этой редакции.
- [x] Inline-гейт в `radar` job (pre-commit, `$CHANGED`-scoped) — реализовано (`5209556`), без изменений в этой редакции.
- [ ] **Goal 2 (ревизия)**: full-scan гейт в конце **каждого** job'а, пушащего в vault (`radar`, `publish`, `patterns`, `analysts`, `check_models`) — после `git pull --rebase origin vault`, до `git push origin vault`. Превентивный: `exit 1` останавливает push. Закрывает не только собственные записи каждого job'а, но и риск получить чужой невалидный файл через rebase от параллельного писателя (Правило 30 CONSTITUTION).
- [ ] **Goal 3 (ревизия, явно сужена)**: `lint_vault` — детективный, не превентивный механизм для пути, который никакой CI-гейт в принципе не может перехватить превентивно: прямой `git push` человека с терминала мимо всех CI job'ов. Триггер — `schedule`/`web`, не `push` (push-триггер удалён как мёртвый, не оставлен декоративно). **Явно принятый компромисс, не молчаливое допущение**: между ручным push'ем невалидного файла и следующим срабатыванием `lint_vault` существует окно, в котором невалидный файл лежит в `vault` необнаруженным. Альтернатива (server-side pre-receive hook / GitLab push rules) не исследована в этой фазе — возможно недоступна на используемом тарифе GitLab, не входит в скоуп.
- [x] `backfill_frontmatter.py` сверяется с `git origin/vault` перед `--apply` — реализовано (`5209556`), без изменений в этой редакции.

## Tech Stack

Без изменений от первой редакции: Python 3, PyYAML, переиспользование `vault_write.parse_frontmatter()`, `pytest`.

Дополнительно: GitLab CI/CD Pipeline Schedule — **не требуется новая настройка** (см. Detailed Requirements §3, `lint_vault` намеренно триггерится на уже существующие schedule-события `radar`/`publish`, а не на отдельное новое расписание).

## Detailed Requirements

### 1. `check_frontmatter.py` — без изменений

`validate_file`/`validate_paths`/CLI — реализовано и протестировано в первой редакции, остаётся как есть. NFR о его чистоте (никаких git/сетевых вызовов) сохраняется без изменений — новая логика (full-scan гейт, Telegram-алерт) размещается в `script:` job'ов, не внутри этого модуля.

### 2. Full-scan гейт в каждом job'е, пушащем в vault (новое)

Позиция: после `git pull --rebase origin vault`, до `git push origin vault`, внутри `else`-ветки (там, где уже определено, что есть что коммитить/пушить).

Вызов (иллюстративно, точный текст — на этапе реализации):
```yaml
- git pull --rebase origin vault
- python3 ../check_frontmatter.py 01_Assessments || exit 1
- git push origin vault
```

Full-scan (весь `01_Assessments/`), не `$CHANGED`-scoped — в отличие от существующего pre-commit гейта `radar`, этот гейт должен ловить и то, что могло прилететь через rebase от параллельного писателя, не только собственные изменения текущего job'а.

Затрагиваемые job'ы: `radar`, `publish`, `patterns`, `analysts`, `check_models` — все пять, у которых есть `git push origin vault` в конце `script:`. `radar` получает этот гейт **в дополнение** к уже существующему pre-commit `$CHANGED`-гейту (Milestone 3, `5209556`) — не взамен: pre-commit гейт дешёвый и быстрый (fail fast, до сети/rebase), post-rebase full-scan гейт — более широкое, но более дорогое покрытие. `publish`/`patterns`/`analysts`/`check_models` не пишут в `01_Assessments/` сами (пишут в `99_System/`, `02_Patterns/`, `04_Analysts/` соответственно) — им нужен только post-rebase гейт, не pre-commit.

All-or-nothing, как и существующий гейт `radar`: `exit 1` до `git push` — ничего не пушится в этом прогоне job'а, включая валидные изменения того же прогона. Следующий плановый прогон подхватит всё заново (STOP_PIPELINE вместо частичного прогресса, Budget Protection).

### 3. `lint_vault` job — ревизия rules

Было:
```yaml
rules:
  - if: '$CI_COMMIT_BRANCH == "vault" && $CI_PIPELINE_SOURCE == "push"'
```

Станет:
```yaml
rules:
  - if: '$CI_PIPELINE_SOURCE == "schedule"'
  - if: '$CI_PIPELINE_SOURCE == "web"'
```

Push-условие удаляется полностью (мёртвое, не оставляется как декоративное). Ветка не проверяется в `rules:` вообще — `script:` и так клонирует `--branch vault` литералом, независимо от того, какой ref вызвал pipeline, поэтому branch-условие избыточно и было нужно только для (нерабочей) попытки триггериться именно на push-событие.

Триггер `schedule` — **намеренно без дополнительной namespace-переменной** (в отличие от `radar`/`publish`, которые используют `$PUBLISH_ONLY`/`$PATTERN_MODE` для отделения друг от друга). Причина: `lint_vault` — read-only детектор (кроме алерта при ошибке, никаких мутирующих операций), нет вреда от того, что он «прицепится» к любому существующему scheduled pipeline (`radar`-cadence и `publish`-cadence оба это `$CI_PIPELINE_SOURCE == "schedule"`). Это даёт периодическую проверку без необходимости заводить владельцу отдельное новое CI/CD Pipeline Schedule в вебе — переиспользует уже существующее расписание. `web` добавлен для ручного прогона по требованию (сам по себе рабочий триггер, уже подтверждён историей pipeline'ов).

`script:` job'а не меняется — та же логика полного скана `vault_repo/01_Assessments` + Telegram-алерт через `curl` при ошибке (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_OWNER_ID`, тот же паттерн, что в `vault_write.py`), уже реализованная и не зависящая от триггера.

### 4. `backfill_frontmatter.py` — без изменений

Сверка с `git origin/vault` перед `--apply` (`5209556`) остаётся валидной без изменений — это защита от отставания локального чекаута, ортогональная триггерам CI, не затронута этой ревизией.

3. `python3 -m py_compile check_frontmatter.py` — уже выполнено, без изменений в этой ревизии (новый код — YAML/bash в `.gitlab-ci.yml`, `py_compile` неприменим).
4. `02_Patterns/` — вне области действия этой фазы (без изменений).
5. **Новое**: full-scan гейт (§2) не должен замедлять job'ы, не пишущие в `01_Assessments/`, сверх необходимого — `check_frontmatter.py` на директории из нескольких десятков `.md`-файлов — операция на чтение, миллисекунды, не требует отдельной оптимизации.

## Security Considerations

Без изменений от первой редакции (никаких новых секретов, `check_frontmatter.py` не интерполирует содержимое в LLM-промпт, `yaml.safe_load`).

**Новое — явный residual risk** (не молчаливое допущение, см. Goal 3): окно между ручным push'ем невалидного файла в `vault` мимо CI и следующим срабатыванием `lint_vault` (schedule/web) — файл в этот период недоступен для детекции. Принято владельцем как компромисс при выборе комбинации (b)+(c) вместо единого превентивного механизма, которого структурно не существует для этого конкретного пути (push с терминала).

## Test Plan

Тестовая ветка `test/lint-vault-check` (созданная под первую редакцию Milestone 6) — **не нужна для этой ревизии**, push-триггер, ради проверки которого она создавалась, удалён. Ветка не удаляется в рамках этой сессии автоматически — отдельное решение владельца.

1. **Unit-тесты `check_frontmatter.py`** — уже реализованы и зелёные (5/5), без изменений, покрывают логику валидации, которую используют оба новых вызова (§2 и `lint_vault`).
2. **Full-scan гейт (§2) — локальная проверка bash-фрагмента**, без реального GitLab CI: прогнать сам фрагмент (`git pull --rebase` / `python3 check_frontmatter.py DIR || exit 1` / `git push`) на локальной тестовой директории с одним заведомо невалидным файлом, подтвердить, что `exit 1` останавливает выполнение до гипотетического push. Не требует пайплайна — это тот же класс проверки, что уже сделан юнит-тестами для самой логики валидации, здесь проверяется только bash `||`-идиома.
3. **`lint_vault` (детективный, §3) — реальный прогон через `$CI_PIPELINE_SOURCE == "web"`**: ручной запуск через кнопку Run Pipeline в GitLab UI (штатная функция, не требует временных коммитов/веток — можно выбрать существующий ref, например `master` или `vault`, `rules:` не проверяет branch). Подтверждает: (а) реальный триггер создаёт реальный pipeline на реальном GitLab Runner (в отличие от push-триггера первой редакции), (б) `script:` job'а реально клонирует `vault` и реально вызывает `check_frontmatter.py`.
   **Явная граница этой проверки, решено 2026-08-04**: поскольку `vault` в текущем состоянии не содержит невалидных файлов (прекондиция, см. ниже), такой прогон подтвердит успешный путь (`success`, ошибок не найдено) и сам факт срабатывания триггера — но не пройдёт по RED-ветке (Telegram-алерт). Решено не воспроизводить RED-ветку через временный невалидный файл в реальном `vault` — риск гонки с production cron (Правило 30 CONSTITUTION) не оправдан, уверенность в RED-ветке уже набрана через unit-тесты `check_frontmatter.py` + локальную проверку идентичной bash `||`-идиомы (Milestone 7).
4. `python3 -m py_compile check_frontmatter.py` — уже выполнено, без изменений.
